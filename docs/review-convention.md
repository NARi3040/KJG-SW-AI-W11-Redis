# 문서 리뷰 규칙

이 저장소는 코드가 아니라 **계획 문서 5개**를 리뷰하는 프로젝트다. 리뷰의 목적은 "무엇을 고쳐야 하는지"를 **줄 단위로 바로 알게 하는 것**이다. 그래서 모든 리뷰는 아래 규칙을 따른다.

---

## 1. 원칙: 지적마다 위치와 수정안을 함께 적는다

본문보다 줄 주석이 낫다. 본문에 쓰면 읽는 사람이 "어느 부분"인지 다시 찾아야 한다.

| 하지 말 것 | 이렇게 |
| --- | --- |
| "issues.md에 `activate`가 빠져 있어요" | `issues.md:79`의 해당 줄에 주석으로 |
| "지적이 맞아요" | "맞아요. 이렇게 고치면 됩니다"를 한 줄로 |

**위치 표기 형식**: `파일명:줄번호` + 해당 줄 텍스트 1줄 복사.
- 좋은 예: `planning.md:96`, `c-hashtable-and-bindings.md:47`
- 나쁜 예: "부하율 계산" (어느 파일 어느 줄인지 알 수 없음)

---

## 2. 리뷰 다는 방법: 본문이 아니라 줄 주석

현재 리뷰는 **본문에 모든 지적을 넣는 방식**이라 읽는 사람이 줄마다 찾아가야 한다. 대신:

### (1) 줄 단위 리뷰: 초안 해제 → 줄 주석 → 리뷰 제출

```powershell
# 1. 초안(Draft) PR은 자동 리뷰가 안 되므로 먼저 해제
gh pr ready 3

# 2. 어떤 줄이 바뀌었는지 확인
gh pr diff 3 --patch

# 3. 정확한 줄에 주석 달기
gh api "repos/OWNER/REPO/pulls/3/comments" `
  -f body="이 줄 명세와 수정안" `
  -f commit_id=$(gh pr view 3 --json headRefOid -q .headRefOid) `
  -f path="docs/planning.md" `
  -F line=96 -f side="RIGHT"

# 4. 본문은 요약과 완료 기준만
gh pr review 3 --comment --body "줄 단위 지적은 Files changed 탭에 있다. 본문에는 요약만 남긴다."
```

→ 확인하는 사람은 **Files changed 탭**에서 바로 볼 수 있다. 본문은 "무엇을 먼저 봐야 하는지"만 담당한다.

### (2) 더 좋은 방법: PR을 쪼개서 하나씩

| 방법 | 설명 |
| --- | --- |
| 본문 리뷰 | 장점은 한눈에 보임. 단점은 **줄을 찾아야 하고, 수정 후 상태 파악이 어려움** |
| **`suggested change`** (```` ```suggestion ```` 블록) | 고칠 내용을 **바로 반영 가능하게** 제시 |
| **이슈로 분해하기** (추천) | "지적 전체를 한 번에" → 줄 단위로 쪼개면 진행률이 보임 |

---

## 3. 가장 실용적인 방법: 리뷰 결과를 "검토 목록"으로 바꾸기

리뷰 5번 = 지적 40건의 진짜 문제는 **하나**다. 리뷰가 길어지면 읽는 사람이 지친다. 그래서 결론:

1. **리뷰는 두 가지 종류만 남긴다.**
   - 맞다 / 맞지 않다
   - 결정 필요: `유지` / `삭제` / `방향`
2. **줄 단위로 구체적인 것은 PR 본문의 체크리스트에 넣는다.** (리뷰에 다 넣지 않는다)
3. 리뷰는 체크리스트 링크만 달고, 수정 진행은 **체크리스트에서** 확인한다.

---

## 4. PR 본문에 붙일 체크리스트 (복사용)

아래 표를 PR 본문에 복사해 `- [ ]` 체크박스로 둔다. 각 리뷰어는 자기 행만 채운다.

| 번 | 위치 | 결정 | 담당 | 상태 |
| --- | --- | --- | --- | --- |
| 1 | `store-and-snapshots.md:166` S-T13 주석 | 철회 | ② | [ ] |
| 2 | `HT_CORRUPT`/`TableCorruptionError` 처리 | 유지 + 조건 기재 | ① | [ ] |
| 3 | `issues.md:79, 219, 223, 269` `activate` 누락 | 반영 | ① | [ ] |
| 4 | `c-hashtable-and-bindings.md:47` 부하율 정수식 | 반영 | ① | [ ] |
| 5 | `planning.md:198, 199, 273` T18 색인 | 반영 | ① | [ ] |
| 6 | `Runtime` 테이블 팩토리 주입 | 결정 필요 | ③ | [ ] |
| 7 | S-T14 접근 스레드 관찰 수단 | 결정 필요 | ③ | [ ] |
| 8 | Windows 강제 종료 시험 완화 | 반영 | ③ | [ ] |
| 9 | 시연(D1,D2)·측정(D3) 순서 재배치 | 반영 | ① | [ ] |

> 리뷰에 이 표만 있어도 "오늘 해야 할 일"이 되고, 위의 리뷰처럼 읽어 오는 일이 없다. 단지 **파일과 줄이 함께** 있어야 한다.

---

## 5. 이렇게 하면 달라진다

| | 지금 | 바꾼 후 |
| --- | --- | --- |
| 리뷰 형태 | 4~5명의 본문 (각 1,000~2,000자) | 본문 10줄 + 줄 주석 |
| 지적 위치 | "issues.md에 …" | `파일:줄번호`를 누르면 줄로 이동 |
| 반영 확인 | "다 고쳤어요" | 체크박스로 "12 / 9 완료" |
| 수정 진행 | 리뷰 5번 = 지적 40건 → 수용 병목 | 작은 PR로 나눠 진행되면 병목이 사라짐 |

---

## 6. 지킬 것

- 이전 리뷰를 다시 읽고 **지적은 본문에 다 넣지 않는다.**
- 리뷰 본문에는 "지적 34건은 줄 주석에 있다"처럼 숫자만 남긴다.
- 새 리뷰는 이 문서를 읽고 **최신 상태에서 미해결 항목부터** 확인한다.
